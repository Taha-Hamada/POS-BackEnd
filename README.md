# POS System — Backend

واجهة برمجية لنظام نقاط البيع، مبنية بـ Node.js و Express و MongoDB.
الفرونت مشروع فلاتر منفصل في `../pos_system`.

## التشغيل السريع

```bash
npm install
cp .env.example .env     # وبعدين غيّر السرّين بتوع JWT
npm run seed             # بيانات بداية للتطوير (اختياري)
npm run dev
```

الخدمة بتشتغل على `http://localhost:5000/api/v1`، وتتأكد إنها شغالة من `GET /api/v1/health`.

المتطلبات: Node 20 أو أحدث، و MongoDB شغالة (محلية أو Atlas).

## أول حساب

لو شغّلت `npm run seed` هتلاقي حساب `admin` بكلمة سر `Admin@12345` — غيّرها فورًا.

من غير الـ seed، أول حساب مدير بيتعمل من `POST /api/v1/auth/bootstrap`.
المسار ده بيرفض أي طلب بعد ما يبقى فيه مدير في النظام، فمش باب خلفي.

## المعمارية

تقسيم بالطبقات جوه فولدر لكل فيتشر، زي ما الفرونت متقسّم بالظبط:

```
route → middleware (تحقق + مصادقة) → controller → service → repository → model
```

| الطبقة | مسؤوليتها |
| --- | --- |
| `*.routes.js` | المسارات، الصلاحيات المطلوبة، ومخطط التحقق |
| `*.controller.js` | يقرأ الطلب، ينادي الخدمة، يرد. مفيش قواعد شغل هنا |
| `*.service.js` | قواعد الشغل كلها. دي الطبقة اللي بتتقرأ عشان تفهم النظام |
| `*.repository.js` | الاستعلامات. الوحيدة اللي بتلمس Mongoose |
| `*.model.js` | المخطط والفهارس والحقول المشتقة |
| `*.validation.js` | مخططات Zod للـ body و params و query |

```
src/
├── config/          البيئة، الاتصال بالداتابيز، اللوجر
├── core/            حاجات مشتركة بين كل الفيتشرز
│   ├── base/        BaseRepository ومخططات التحقق المشتركة
│   ├── constants/   الأدوار والصلاحيات وكل الـ enums
│   ├── db/          العدّادات المتسلسلة ومساعد الـ transactions
│   ├── errors/      ApiError
│   ├── http/        شكل الرد الموحّد و asyncHandler
│   └── utils/       الترقيم وحسابات الفلوس
├── features/        كل فيتشر في فولدره
├── middlewares/     المصادقة، التحقق، معالج الأخطاء، حدود المعدل
├── routes/          تجميع راوترات الفيتشرز
├── db/seed/         بيانات البداية
├── app.js           تركيب تطبيق إكسبريس
└── server.js        نقطة التشغيل والإغلاق المرتّب
```

## قرارات تصميم تستاهل الشرح

**الرصيد مفصول عن المنتج.** المنتج فيه السعر والتكلفة، والرصيد في مجموعة `Stock`
سطر لكل منتج في كل فرع. كده الفروع بتعدّل كمياتها من غير ما تتزاحم على نفس المستند.

**كل تغيير في الرصيد له سطر.** `StockMovement` سجل بنضيف عليه بس ومبنعدلش،
وكل الفيتشرز بتعدي على `applyStockMovement` بدل ما تلمس الرصيد بنفسها.
لو رصيد بان غلط، السجل بيوريك كل حركة والرصيد بعدها.

**الخصم من الرصيد ذرّي.** شرط توفر الكمية بيتحط في فلتر التعديل نفسه،
فالتحقق والخصم بيحصلوا في عملية واحدة ومفيش طلبين متوازيين ينزلوا الرصيد تحت الصفر.

**حسبة الفاتورة دالة صافية.** `invoice.pricing.js` مبتلمسش داتابيز ولا وقت،
فنفس المدخلات بتدي نفس النتيجة، والبيع والمرتجع بيستخدموا نفس الحسبة.
الترتيب: خصم السطر، بعدين خصم الفاتورة، وآخر حاجة الضريبة على الأصناف الخاضعة بس،
وخصم الفاتورة بيتوزع على الوعاء الضريبي بالتناسب.

**الفاتورة بتخزن اللي حصل وقتها.** اسم المنتج وسعره وتكلفته بيتخزنوا في السطر،
فتغيير السعر النهاردة مبيغيّرش فاتورة الشهر اللي فات ولا تقرير أرباحها.

**التوكن مش مصدر الثقة الوحيد.** كل طلب بيقرأ المستخدم من الداتابيز،
فتعطيل حساب أو تغيير دور أو صلاحية بيسري فورًا من غير استنى انتهاء التوكن.
وتغيير كلمة السر بيقدّم `tokensValidFrom` فكل الجلسات القديمة بتسقط.

**الصلاحيات محسوبة مش متخزنة.** الدور بيحدد الباقة، والمستخدم ليه إضافات واستثناءات فوقها،
فتعديل باقة الدور بيسري على كل اللي عليه من غير هجرة بيانات.

**التوقيت موحّد في التقارير.** التجميع بيقسّم الأيام بتوقيت السيرفر مش UTC،
عشان مبيعات آخر ساعات اليوم متقعش في يوم تاني وتختفي من الرسم.

**الـ transactions اختيارية.** لو الداتابيز replica set، العمليات المركبة بتتلف في transaction.
لو سيرفر واحد محلي، بتتنفذ من غيرها والخدمة بتشتغل عادي — ده مقصود عشان التطوير المحلي.

## المسارات

كل الردود بالشكل ده:

```json
{ "success": true, "message": "...", "data": ..., "meta": { "pagination": {...} } }
```

والأخطاء:

```json
{ "success": false, "message": "...", "error": { "code": "INSUFFICIENT_STOCK", "details": [...] } }
```

| المجموعة | أمثلة |
| --- | --- |
| `/auth` | bootstrap, login, refresh, me, change-password, logout-all |
| `/users` | CRUD، إعادة تعيين كلمة السر، تعديل الصلاحيات، كتالوج الأدوار |
| `/branches` | CRUD، فتح وقفل الفرع |
| `/categories` | CRUD بمستوى تفريع واحد |
| `/products` | CRUD، بحث، باركود، تعديل أسعار جماعي، قرب الصلاحية |
| `/inventory` | الأرصدة، الحركات، تسوية، جرد، تحويل بين الفروع، تنبيهات النقص |
| `/customers` | CRUD، كشف الحساب، السداد، نقط الولاء والاستبدال |
| `/suppliers` | CRUD، سداد المستحقات |
| `/invoices` | بيع، تعليق، إتمام المعلّق، إلغاء، ملخص |
| `/returns` | الأصناف المتاح إرجاعها، تنفيذ المرتجع |
| `/shifts` | فتح، حركات الدرج، تقفيل، الوردية الحالية |
| `/expenses` | CRUD، اعتماد ورفض، ملخص بالبنود |
| `/purchase-orders` | مسودة، تأكيد، استلام كلي أو جزئي، إلغاء |
| `/reports` | داشبورد، سلسلة المبيعات، أفضل المنتجات، الأقسام، الكاشيرين، الضريبة، المخزون |
| `/settings` | إعدادات المتجر والضريبة والولاء |

## الأدوار

| الدور | باختصار |
| --- | --- |
| `admin` | كل حاجة، ومش مربوط بفرع |
| `manager` | كل شغل الفرع ماعدا إدارة النظام والفروع |
| `cashier` | بيع، مرتجع، وردية، عملاء، وقراءة المنتجات |
| `accountant` | قراءة كل حاجة، وإدارة واعتماد المصروفات |
| `stock_keeper` | المنتجات والمخزون والمشتريات |

الصلاحيات الفعلية = باقة الدور + الممنوح للمستخدم − المسحوب منه.

## البيئة

الملف بيتتحقق منه عند التشغيل، وأي متغير ناقص أو بصيغة غلط بيوقف السيرفر من أول ثانية
بدل ما يقع في نص الشغل. شوف `.env.example` للقايمة كاملة.

المتغيرات اللي لازم تتغير قبل أي نشر: `JWT_ACCESS_SECRET` و `JWT_REFRESH_SECRET`
و `CORS_ORIGINS` (خليها قايمة نطاقات محددة مش `*`).
